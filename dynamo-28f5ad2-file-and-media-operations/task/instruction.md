Build a reusable recovery program at `/app/restore_design.py`, then use it to reconstruct the job in `/app/design_job/manifest.json`. The same recovery contract is packaged for reference at `/app/recovery_rules.md`; it is agent-visible documentation, not an answer key.

The program must accept exactly three arguments: input job directory, output PPM path, and output JSON report path. A job manifest contains a `canvas`, `palettes`, `fragments`, and optional `repair_groups`. Fragment `path`, optional `mask_path`, and repair shard paths may be absolute or relative to the job directory. Fragment rasters, masks, and repair shards are PGM files; both text `P2` and binary `P5` encodings are valid, with comments allowed in the PGM header. PGM max values from 1 through 65535 are valid. If the max value is not 255, scale each stored sample to the 0-through-255 task domain with `floor(sample * 255 / max_value + 0.5)` immediately after reading; binary `P5` files with max value greater than 255 store each sample as two big-endian bytes. In fragment rasters, scaled sample value `255` is transparent and scaled sample value `254` is a registration marker; neither is painted. Mask samples are scaled coverage values from 0 through 255. A fragment may set `mask_polarity = "inverse"`, in which case use `255 - mask_sample` after mask repair, scan normalization, orientation, and max-value scaling; missing `mask_polarity` or `"normal"` uses the mask sample directly. A path written as `repair:<id>` must be reconstructed from the matching repair group by bitwise-XORing every listed shard sample at the same coordinate; all shards in a group have identical dimensions, and the reconstructed raster is then handled like an ordinary stored raster. For `scan = "serpentine"`, stored rows are numbered from zero; reverse rows whose 0-based `y` index is odd (`y % 2 == 1`) before any orientation is applied. Apply scan normalization before orientation. A fragment raster uses the fragment's `scan` and `orientation`; a mask uses `mask_scan` and `mask_orientation` when those fields are present, otherwise it uses the fragment's `scan` and `orientation`. Orientations are `none`, `rot90`, `rot180`, `rot270`, `flip_x`, and `flip_y`. Rotations are clockwise. `flip_x` mirrors left-right by reversing each row; `flip_y` mirrors top-bottom by reversing row order. After raster and mask repair, scan normalization, orientation, and mask polarity, a fragment may have `source_window = {"x", "y", "width", "height"}` in transformed fragment coordinates; the window lies inside the transformed raster, discard samples outside it, crop both raster and mask to it, and rebase the kept top-left to `(0,0)` before registration or origin placement. Most fragments use integer `x` and `y` as their top-left canvas origin. If a fragment has a `registration` object instead, first apply repair, scan normalization, orientation, and any source window to the fragment raster, then find every `254` marker coordinate in that transformed raster. Translate those marker coordinates so their set exactly equals `registration.canvas_points`; use the unique translation as the fragment origin. The listed canvas points are unordered.

For each fragment, choose the palette revision for its `palette` with the greatest `effective_at` value that is less than or equal to the fragment's `captured_at`. Palette revisions may be complete or partial: build the usable palette by applying every revision with that name and `effective_at <= captured_at` in ascending `(effective_at, revision)` order, with later `colors` and optional `aliases` entries replacing earlier entries for the same key while omitted keys keep earlier values; report the id of the last applied revision. An alias maps a stored sample index to another palette index after transparent/registration handling but before color lookup. Apply fragments in ascending `(z, captured_at, id)` order. Each nontransparent sample has alpha `fragment.opacity * mask_sample / 255`; missing `opacity` means `1.0`, and a missing mask means coverage `255` everywhere. In `mode = "over"`, the source color is the alias-resolved sample's palette color. In `mode = "erase"`, the source color is the canvas background color. In `mode = "atop-background"`, paint the alias-resolved sample's palette color only if the current destination pixel is still exactly the canvas background color; otherwise leave the pixel unchanged. Composite any painted source over the current pixel in linear-light sRGB with per-sample rounding, not directly in 8-bit sRGB; see `/app/recovery_rules.md` for the transfer curve and rounding. Samples outside the canvas after orientation and source-window rebasing are ignored.

Write the recovered image to `/app/recovered_sheet.ppm` as a valid RGB PPM with the manifest canvas dimensions and max value 255. Write `/app/recovery_report.json` as UTF-8 JSON with exactly these keys: `width`, `height`, `applied_fragments`, `palette_revisions`, `rgb_sha256`, `opaque_pixel_count`, `background_pixel_count`, and `processing_audit`. `applied_fragments` is the ordered list of fragment ids. `palette_revisions` maps each fragment id to the selected palette revision id. `rgb_sha256` is the SHA-256 hex digest of the final raw RGB byte stream in row-major order. Pixel counts are over the final canvas; a background pixel is exactly the canvas background color, and an opaque pixel is any other color.

`processing_audit` must be a JSON object with exactly these integer keys: `palette_revision_count`, `repair_group_reads`, `repair_sample_xor_count`, `transparent_sample_count`, `registration_marker_count`, `clipped_paint_sample_count`, `zero_alpha_sample_count`, `painted_sample_count`, `erase_sample_count`, `blocked_atop_sample_count`, `remapped_sample_count`, and `window_discard_sample_count`. Counter sampling semantics match `/app/recovery_rules.md` and are counted while processing fragments in `(z, captured_at, id)` order.
