The SQLite warehouse at `/app/data/warehouse.db` must be reported point-in-time correct as of the cutoff in `meta` where `key = 'cutoff_utc'`. All timestamps are UTC `YYYY-MM-DDTHH:MM:SSZ`, so string order is time order. Write `/app/out/metrics.json`, and write a reusable `/app/out/analyze.py` that runs with `python3 /app/out/analyze.py`, reads `DB_PATH` and `OUTPUT_PATH` env vars, and defaults to `/app/data/warehouse.db` and `/app/out/metrics.json`.

Ignore orders with `ordered_at > cutoff`. For each remaining `orders(order_id, customer_id, product_id, ordered_at, quantity)` row, compute recognized units from `order_status_events(event_id, order_id, event_at, status, units)` using only events with `event_at <= cutoff`, sorted by `(event_at, event_id)`. Start at 0: `confirmed` sets units to the order quantity, `refunded` subtracts event units, `reinstated` adds event units, and `void` resets to 0. Clamp the final value to `[0, quantity]`; zero-unit orders contribute no revenue.

`product_versions(row_id, product_id, effective_from, recorded_at, unit_price_cents, category)` is bitemporal. Build the product timeline known at cutoff by dropping rows with `recorded_at > cutoff`, then keeping, for each `(product_id, effective_from)`, the row with greatest `(recorded_at, row_id)`. An order's base version is the surviving row for its product with the greatest `effective_from <= ordered_at`; if none exists, the order contributes no revenue. The group category always comes from this base version.

The protected unit price is the minimum `unit_price_cents` among the base version and later surviving versions for that product with `ordered_at < effective_from <= cutoff`. Customer loyalty uses `loyalty_tiers(min_prior_units, discount_bps)`: process each customer's orders with `ordered_at <= cutoff` in `(ordered_at, order_id)` order, choose the greatest tier whose `min_prior_units` is `<=` strictly prior cumulative recognized units, then add the current order's recognized units to the running total. All orders with `ordered_at <= cutoff` advance loyalty history after clamping, even if they have zero units or no base version. Discounted unit price is `protected_price - (protected_price * discount_bps) // 10000`.

`customer_aliases(row_id, customer_id, canonical_customer_id, effective_from, recorded_at)` is bitemporal. For any order or credit timestamp, drop alias rows with `recorded_at > cutoff`, then for that original `customer_id` choose the row with greatest `(effective_from, recorded_at, row_id)` among rows with `effective_from <= timestamp`; if none exists, keep the original id. Do not recursively follow aliases. Use this resolved account id, not the raw customer id, for loyalty history and credit consumption.

Before grouping, apply `account_credit_events(credit_id, customer_id, issued_at, expires_at, amount_cents)`. Ignore credits with `issued_at > cutoff`. For each resolved account, process qualifying revenue orders in `(ordered_at, order_id)` order. A credit is available when its resolved account matches the order, `issued_at <= ordered_at`, and `expires_at > ordered_at`; expiration is exclusive. Drop expired or exhausted credits before each order, then consume remaining line revenue from available credits ordered by `(expires_at, issued_at, credit_id)`. Credits reduce revenue after loyalty pricing, but do not change recognized units, loyalty history, or order counts.

Pre-credit line revenue is `recognized_units * discounted_unit_price`. A qualifying revenue order is an order with positive recognized units and a surviving base product version; zero-unit and no-base-version orders are excluded from grouping and `order_count`. Group qualifying revenue orders by `ordered_at[:7]` month and base category. Count qualifying revenue orders before credits and sum post-credit line revenue.

`/app/out/metrics.json` must be a JSON object with exactly:

- `cutoff_utc`: string, the cutoff value.
- `rows`: array of objects, each with exactly `month` (string `YYYY-MM`), `category` (string), `order_count` (integer, qualifying revenue orders in the group), and `net_revenue_cents` (integer, summed line revenue). Include only groups containing at least one qualifying revenue order. Sort the array ascending by `month`, then by `category`.
