# Project Dynamo Learnings

Use this as the default root-level checklist for faster Dynamo task development. Add broad, reusable lessons here; keep deep difficulty strategy notes in `PROJECT_DYNAMO_STUMP_GUIDE.md` and review-scoring rules in `project_dynamo_reviewer_notes.md`.

## Fast Development Loop

- Pick the task's real crux before editing data, instructions, or tests.
- Write the contract first: data assumptions, edge cases, output schema, tie-breaks, tolerances, ordering, and exact-format requirements.
- Walk the actual dataset against the contract. If duplicates, nulls, stale records, symlinks, zero-value rows, or late corrections exist, either document them or change the data.
- Build oracle, verifier, and hidden tests from the same rule. Do not let hidden tests enforce a rule missing from `instruction.md`.
- Run a bad-output or nop check early. A verifier that accepts placeholders, empty files, copied scaffolds, or fake but plausible output is not ready.
- Check fail reasons after pass runs. A `0/5` from timeouts, stuck agents, provider errors, or setup failures is not valid model-stumping evidence.
- Before PR submission, do a fresh-review pass: instructions, data, tests, solution, task metadata, screenshots, and pass/fail evidence should all tell the same story.

## Cloud Agent Docker / Harbor Gotchas

- On Cursor Cloud Agent VMs, install `docker.io` + `docker-compose-v2` and start `dockerd` with `storage-driver: vfs`. Overlay often fails.
- Harbor Compose may still fail with cgroup v2 `threaded mode` inside nested containers. That is infrastructure, not a task defect.
- Fallback: `docker run --privileged --cgroupns=host` with `/solution` RO and `/tests` RW, then run `solve.sh` + `test.sh` for oracle and `test.sh` alone for nop. Expect rewards `1.0` / `0.0`.
- Full procedure: `CLOUD_AGENT_DOCKER_HARBOR.md`.

## Static Check Gotchas

- If `task/environment/` has a non-trivial Docker build context, especially a `data/` subdirectory copied into `/app/data`, add `task/environment/.dockerignore` before opening the PR. The Dynamo static gate fails fast with `non-trivial build context (has subdirectories) but no .dockerignore`.
- A minimal task data context usually works as:

```dockerignore
*
!Dockerfile
!data/
!data/**
```

- Keep the `.dockerignore` narrow: include only the Dockerfile and agent-visible environment assets. Never include `solution/`, `tests/`, local Harbor `jobs/`, or generated outputs in the Docker build context.
- Run the static-ish local checks before committing: `git diff --check`, `bash references/check-base-image.sh task`, and a scaffold scan such as `rg -n "Replace this file|TODO|placeholder|pass$|dummy|your-task-name" README.md task`.

## GitHub CLI Gotchas

- When multiple GitHub CLI accounts are cached locally, `gh` can flip back to a different active account after fork, PR, or check-watching commands. Before pushing, creating a PR, reading private run logs, or watching checks, run `gh api user --jq .login` and switch back to the intended account if needed. A wrong active account often appears as a confusing private-repo `404`, even when the repo, fork, PR, or run exists.
- Enforced cosine no-verdicts with `HTTP status: 401` are service-auth/infrastructure failures when the sticky contains no similarity scores and all downstream checks are skipped. A single empty retry commit is reasonable; repeated identical 9-10s `401` failures are not task-design evidence and usually require platform-side recovery before AVA/QC/trials can rerun.

## R1 Rejection Checks: Coherent Contract

- Documentation must describe the actual shipped dataset, not an idealized version of it.
- Mirror decisive tie-breaks, precedence rules, and data anomaly semantics in shipped fixture docs when those docs are part of the visible evidence. QC may treat a rule as underdetermined if `instruction.md` says it but the manifest notes/examples around the anomaly do not.
- Never state guarantees that the data violates, such as "no duplicates," "no nulls," sorted input, exhaustive buckets, unique IDs, or blank values only in one range.
- Byte-identical duplicate rows still matter. If the solver is told each key appears once, it may reasonably skip dedupe logic and then crash or corrupt state when real duplicates appear.
- If duplicates are valid, state their semantics plainly, for example whether they are redundant replay rows to drop, conflicts to resolve, or repeated events to sum.
- If a defensive rule exists in the reference solution, tests should exercise it and instructions should make it discoverable.
- If a hidden fixture introduces a present-but-malformed optional sidecar, explicitly state the malformed-file policy in `instruction.md`; saying only what a valid sidecar looks like and how value mismatches behave can still trigger QC B6.
- If two rules conflict on real data, fix the written contract first, then align the oracle and verifier.
- For signed integer arithmetic, never rely on `//` being self-explanatory across languages. State floor-vs-toward-zero rounding explicitly and include at least one negative-value fixture when the distinction affects output bytes.
- QC may fail B3 with sparse or empty rendered evidence. Check adjacent missing-definition hazards: fixture docs pointing to non-shipped files, report counters named but not defined, schema fields whose JSON types are only implied, and advertised inferred behaviors that hidden fixtures never positively witness.
- Useful source for this check: https://project-dynamo.learn.joinhandshake.com/practice/coherent-contract

## R1 Rejection Checks: Brittle Verifier

- The verifier should accept every answer format reasonably allowed by the instructions.
- If the verifier accepts only one exact string, byte sequence, order, casing, spacing, tolerance, or file layout, that exact requirement must be explicit in `instruction.md`.
- Prefer semantic assertions for the promised behavior over snapshot-only checks when multiple outputs are equally valid.
- When exact JSON integer output is part of the contract, use recursive type-aware equality. Python parsed-JSON equality accepts `5.0 == 5`, and loose `isinstance(x, int)` can also let booleans through.
- If the instruction says a solver must recover a policy branch such as routing, sign, gain direction, or drift direction, include at least one visible or protected witness where trusting the default/field-name interpretation changes a graded output.
- Do not punish harmless implementation differences. Reserve exact-byte or exact-format checks for tasks where formatting is the domain challenge.

## R1 Difficulty Checks: Timeout Is Not Wrong Answer

- A `0/5` result is only useful if at least one run produced a complete, gradable wrong answer.
- Open the fail reasons instead of relying on the pass/fail banner.
- Treat all-run timeouts, stuck loops, infrastructure errors, provider failures, and setup failures as budget or packaging signals, not proof that the model was stumped.
- If every run timed out or got stuck, increase the execution budget or reduce mechanical workload and rerun before claiming difficulty.
- Related source: https://project-dynamo.learn.joinhandshake.com/stump-the-model

## R1 Rejection Checks: Starter Scaffold

- Do a final pass before PR submission to ensure starter-template boilerplate has been replaced.
- Reject-risk examples: placeholder tests, empty `solve.py`, unused scaffold files, or tests that pass regardless of output.
- Review the repo from a fresh reviewer perspective before submitting.
- Verify tests fail on an incorrect or missing solution, not just on malformed files.
- Search for starter/template markers such as `TODO`, `pass`, `placeholder`, dummy expected values, and tests that only assert file existence.

## R1 Rejection Checks: Gameable Tasks

- Try to beat the verifier with a fake or non-solving submission.
- Keep ground truth outside paths the agent can read or write during the task.
- Do not expose reference answers or expected outputs inside the runtime environment.
- Ensure the test runner cannot be replaced, redirected, symlinked, or bypassed by agent-controlled files.
- Avoid verifier logic that recomputes truth from agent-writable input.
- For reusable solver hidden cases, compute expected answers and input hashes before launching the submitted tool. Run the child on read-only inputs where possible and assert the input tree hash is unchanged afterward; otherwise a tool can mutate the generated fixture and make the verifier recompute the attacker's easier truth.
- For reusable-tool grading, do not let verifier-time tool subprocesses inherit cwd `/tests` or read verifier source. Use a safe cwd, drop root to an unprivileged uid when available, open temp pack permissions only for that child, and hide `/tests` during the child run.

## R1 Rejection Checks: Consistency And Coverage

- Walk through `instruction.md` using the actual dataset to catch contradictory rules.
- Compare the reference solution output against the written instructions line by line.
- Tests should verify the real crux, not only formatting or loose thresholds.
- Ask whether someone could hardcode, fake, or broadly satisfy the tests without solving the task; strengthen tests if yes.
- Ensure the agent cannot influence any file, data source, or symlink target used to verify correctness.
- For per-frame sidecars combined with transforms, offsets, clipping, or resampling, name the exact coordinate system. State whether arrays index source frames, transformed clip frames, or destination/output frames, and whether skipped or clipped-away frames reindex later values.
- If instructions use standard transform terms such as clockwise 90/180/270 rotation, the reference and verifier must implement the standard coordinate mapping. A non-standard mapping hidden only in oracle/test code will be classified as a task/verifier issue; either use the standard formula or disclose the exact mapping with a visible witness.
- For manifest/report counters, avoid informal terms such as "final" unless that stage is defined. Tie each counter to exact pipeline state, such as selected event, overridden base value, effective per-frame value, post-transform offset, rendered placement, or preserved input.
- QC may treat a rule as underdetermined when it is only in the task prompt and not visible in shipped fixture notes. For decisive sort orders and report counters, mirror the rule in a benign agent-visible note and include a held-out witness where the alternative changes output.
- Hidden-only optional sidecars still need exact schemas in agent-visible material. If hidden tests include files such as `masks.tsv` or `windows.tsv` that are absent from the visible fixture, state every enforced column name in `instruction.md` and mirror the schemas in visible fixture notes when practical.
- Decisive event supersession, tie-break, and ordering markers should be mirrored in visible fixture notes as well as `instruction.md`. QC B5 may test whether visible in-box evidence plus disclosed outputs distinguishes rival mappings, such as `(known_at,event_id)` versus `(known_at,version,event_id)`.
- Verifier symlink checks must reject every output path component, not only the leaf file. Also run pytest from a protected non-agent-writable directory such as `/tests` with isolated Python mode (`python3 -I -m pytest`) or a console-script path so cwd-on-sys.path module shadowing cannot hijack reward plumbing.
- For input path-safety checks, include a symlinked intermediate component that points back inside the allowed tree. Escapes and leaf symlinks do not catch mutants that keep `resolve().relative_to(base)` but drop the explicit per-component symlink probe.
- Avoid committing symlinks into visible Docker-copied fixtures unless you have verified the exact platform preserves them. A safer pattern is to generate symlink witnesses inside protected verifier temp directories and keep the shipped visible fixture symlink-free.

## Apply During Task Work

- Before pushing, run a scaffold scan for placeholders and starter remnants.
- Run or simulate a nop/bad-output check to prove the verifier fails when the task is not solved.
- Confirm `environment/` does not copy `solution/`, `tests/`, or expected outputs.
- Confirm instructions, oracle, tests, and metadata describe the same rules.
- Prefer oracle-derived expected values so verifier fixtures do not drift from the reference implementation.

## R1 Difficulty Checks: Visible Instance Solved

- If `pass@2` solves the visible task cleanly, strengthen the semantic/generalization crux rather than adding vague or undisclosed traps.
- If pass@2 solves because agents transcribed a fully specified formula-level prompt, convert at least one decisive subsystem into an explicitly agent-visible inference problem. Keep output/schema/fairness rules exact, but make per-instance internals such as codec constants, checksum salts, or clock statistics recoverable from calibration evidence and varied across protected reusable-tool fixtures.
- For reverse-engineering tasks, do not leave the function class completely implicit. State the recoverable family (for example compact arithmetic transition system, fixed table families, current-state fields used) while withholding exact constants for the corpus to identify; otherwise QC B5 may treat the task as underdetermined hidden knowledge.
- Requiring a reusable artifact, such as an importable solver entry point, can expose hardcoding and visible-instance tuning while remaining fair when the full rules are disclosed.
- For reusable solver/tool artifacts, a small finite set of fixed protected fixtures can still be AVA-gameable by hidden-input fingerprint lookup tables. Prefer deterministic metamorphic or submission-salted protected cases, while still computing expected answers from protected rules instead of solver-writable outputs.
- For reusable CLI verifiers, do not generate expected outputs beside the input fixture given to the submitted tool. Use a separate non-traversable temp tree for answer keys, invoke the submitted CLI on visible fixtures as well as hidden fixtures, and byte-compare JSON when the prompt specifies canonical JSON formatting.
- Hidden reusable-solver cases should vary structural domains, not only constants: precision/id ranges, candidate counts, topology width, schema variants, and modulus sizes. Keep these variants small enough that correct solvers fail/pass by semantic generality rather than memory or timeout pressure.
- For file/media restoration tasks, hidden reusable-tool fixtures should vary manifest-level shape such as dimensions, frame count, and fps when the instruction says to derive them; varying only record content may still leave the visible artifact too easy to clone.
- If pass@2 solves a fully specified file/media renderer 2/2, make protected fixtures structurally different from the visible skeleton: change source count, codec combinations, revision-chain depth, repair density and invalid repair placement, transform geometry on non-square canvases, and feedback/tap topology. Also remove redundant fixture-local notes that rephrase every formula in the prompt unless they are needed to disambiguate visible in-box evidence.
- For policy-driven file/filter CLIs, hidden reusable-tool fixtures should vary the policy surface itself, not only the records. Change region/order lists, thresholds, caps, weights, and marker parameters across protected seeds, and include marker classes whose effects interact with selection, scoring, rejection counters, and copy output.
- For reusable file/filter verifiers, semantic seed diversity must include identifiers and lifecycle fields too. If protected fixtures reuse the visible record-id skeleton, priorities, timestamps, marker ids/statuses, bonuses/deltas, and profile magic/bounds, AVA may show that a literal answer-table solution passes; add a small diversity meta-test that compares generated TSV contract fields across seeds.
- Hidden verifier cases should exercise legitimate edge cases from the written rules, such as point-in-time revisions, cross-region connectivity, delayed events, and broader legal choices.
- Make sure hidden cases are not just extra busywork: they should fail a plausible shortcut for a concrete professional reason.
- If pass@5 still solves, add a deeper algorithmic hidden crux rather than merely another instance. For decomposed optimizers, global modulo objectives are a strong fair trap because local component optima can combine to the wrong wrapped residue.
- If final pass@5 has only one valid fail, broaden hidden coverage across independent disclosed semantics. Multiple small hidden scenes that each target a different common shortcut can be stronger than one large scene: ordered same-tick memory, pre-effective portal behavior, delayed-release boundaries, prism batching, and modulo-residue optimization each catch different incomplete solvers.
- If final pass@5 still has too many solves after semantic broadening, add a disclosed algorithmic scale check. For optimizer tasks, a wide single component with many candidate cells and exact placement count can catch full product enumeration, greedy selection, and unsafe pruning while still being fair to a reusable solver.
- Deep review can fail even when pass@2 proves difficulty if a hidden assertion depends on behavior not uniquely disclosed in `instruction.md`. Every hidden edge case must be pinned by agent-visible text, especially fallback/default behavior before time-based rules become effective.
- If a hidden performance/scale trap depends on rejecting brute force, disclose the size or runtime requirement without naming the intended algorithm. Say the candidate space may be too large for full enumeration and give the verifier time budget; do not write hints such as "use DP" in `instruction.md`.
- Pass@2 does not count verifier-kill timeouts as valid difficulty. Calibrate scale traps so slow or shortcut solvers finish and fail by ordinary assertion diffs, then pair them with fast semantic edge cases that produce structured CTRF failures.
- If pass@2 agents solve every hidden case with legitimate optimized algorithms, increase difficulty by adding fully disclosed state dimensions or topology changes that require solver redesign, such as candidate-placed portals, heat-history filters, phase-dependent tiles, color mutation, and renderer saturation checks. Keep these cases small enough to finish quickly so failures remain valid test failures.
- If pass@2 failures are only format serialization defects after agents solved the core algorithm, disclose the exact serialization in the visible contract and add one real, documented lifecycle/topology crux in the same revision. For simulation tasks, current-tick partial-state readers before routing/table lookup are a fair ratchet because they affect ordering, state, metrics, events, and audit output together.
- For file/media renderer tasks solved 2/2 near the time budget, prefer one disclosed subsystem that rekeys the render loop and report accounting over random extra fixtures. Per-frame sidecar programs that alter source samples, destination positions, effective gains, and counters can add valid difficulty while staying fair if visible notes and hidden generated witnesses cover them.
- If a new per-frame sidecar is still solved by transcription, make the next fair ratchet depend on current rendered state, not only static clip/frame data. A disclosed feedback/tap sidecar that reads the partially rendered bus before compositing can rekey ordering, clipping, splice, under/over, and counter logic; include a visible TSV witness plus generated hidden witnesses and verify an ignore-sidecar mutant fails.
- For audio/session repair tasks that become 2/2 solved after fairness fixes, a visible cross-chunk tap sidecar can be a focused ratchet: read already-rendered source chunks only, include a future-source row that must be ignored, vary modulo/stride/gain/order in hidden cases, and make `taps_applied` affect both track and total reports.
- For image atlas/compositing tasks that become 2/2 solved as fully specified renderers, a documented `feedback.tsv`-style sidecar can add fair difficulty by sampling the current partially rendered atlas before the current layer composites. Mirror the schema in visible notes, include at least one visible active row, vary channels/offsets/gains in hidden generation, and add exact layer/pixel counters.
- If that still yields 2/2 full solves, target assumptions inside otherwise-correct simulators: add disclosed rules that depend on global state accumulated during the current tick, not only local cell heat or static tile transitions. These catch solvers that precompute tile transitions or update temporal accounting after routing.
- If pass@2 still solves stateful simulator additions, add a disclosed optimization-objective variant that breaks the most common exact architecture. For this beam task, `peak_bonus * peak_load` forces solvers to account for temporal aggregation during optimization, not only final beam checksum residues.
- If pass@2 cleanly solves a small fully specified simulator after ambiguity fixes, add a disclosed mutable-state subsystem that changes future simulation semantics and winner selection, not only a new output field. Post-tick switches, portals, locks, or similar devices should affect routing/table lookup, metrics, tie-breaks, audit, visible fixtures, salted hidden fixtures, and a negative mutant check.
- If pass@2 still solves that mutable-state subsystem, add a disclosed rule that mutates future scheduled work rather than only future static state. Gates, hold queues, or deferred actions should inspect current rendered state, select already-pending future work in a documented stable order, reschedule or drop it, and feed metrics, rank vectors, audits, visible fixtures, salted hidden fixtures, and a targeted ignore-feature mutant.
- For performance cruxes, prefer a test-level subprocess timeout around one targeted hidden scene instead of letting pytest or the whole verifier time out. This converts brute-force failures into structured assertion failures while keeping oracle validation fast.
- For placement optimizers solved by full candidate/tile enumeration, add a disclosed sparse-scale hidden case where the nominal search space is huge but exact solvers can prune by replay reachability. Document how never-entered selected candidates affect only the tie-break, then validate that the reference branches on first live contact with an undecided candidate instead of enumerating inert placements.
- For simulator tasks with a legal tile/operator alphabet, include at least one protected witness for each advertised operator family. QC will mutate unused branches such as absolute arrows or delay release semantics, and prose alone is not enough if the verifier never forces those branches to affect exact outputs.
- For any documented "process in sorted order" rule, include a held-out witness with at least two valid same-bucket records whose outputs differ, so reversing or ignoring the sort order changes a graded artifact. Assert the selected identifier in provenance/report output when available.
- For threshold predicates with multiple conjuncts, include both positive and negative witnesses. A lock example that always opens does not distinguish hue-only, state-only, and key-plus-state threshold rules; add a same-category-but-too-weak case where the action must fail.
- For rare successful events, do not document only the eligibility predicate. If the verifier scores post-success state or report consequences, either state the exact consequence arithmetic in visible material or include multiple visible successes that vary each factor and separate the event bonus from ordinary downstream effects.
- When a checksum or event formula mixes pre-event and post-event state, label every mixed-stage variable explicitly. Annotating only one old-state field can make adjacent unannotated fields look old-state by analogy, even if sequential execution would otherwise imply post-update state.
- Inclusive thresholds need equality-boundary witnesses. A `>=` contract is not covered by above-threshold successes and below-threshold failures; include a case where equality must pass, and keep hidden numeric ranges within visible/disclosed domains unless the prompt explicitly says broader ranges are valid.
- If accumulation uses per-add saturation, clipping, or any non-associative operation, document the exact accumulation order and make the oracle use that canonical order rather than incidental dict or ledger insertion order. Pair path-safety requirements with full-schema absolute and `..` path witnesses; malformed rows that mention unsafe paths do not prove the path checks are enforced.
- Seed every verifier-generated graded cohort with fixed constants unless the task deliberately uses a reviewed anti-lookup salting scheme. QC can reject `secrets`/`os.urandom` hidden generation as nondeterministic even when expected outputs are recomputed by the oracle.
- For every inclusive/exclusive filter boundary, add a protected equality witness where changing `>` to `>=`, `<` to `<=`, or the reverse changes both an artifact and a report field. Do this proactively for cutoffs, time windows, frame ranges, revision bounds, and array index windows.
- For compound validation predicates, cover each conjunct independently. A single malformed row with `start < 0` does not prove `stride <= 0`, empty values, out-of-range indexes, or clipping checks are enforced; add separate held-out witnesses so mutating any one guard changes exact outputs.
- For secondary sort-key mutation coverage, data with tied primary keys is not enough if the oracle's input iteration order already matches the documented secondary key. Feed the final `sorted()` call from a deterministic non-secondary-key order and add visible/protected ties where deleting the secondary key changes an artifact.
- For reject-counter reports, every bucket must have an explicitly documented policy and at least one witness that reaches that stage after passing earlier gates. A malformed-schema row with an unsafe path does not witness path bucketing, and no decode-invalid valid packet lets a decode-error-to-wrong-counter mutant pass.
- If a task tells solvers to infer profile rules from a fixture-local note, mirror every decisive non-profile rule that affects visible outputs in that note too: duplicate policy, output ordering, and list element shape. Also harden `test.sh` by changing to a protected verifier directory and using isolated Python (`-I`) so `python -m pytest` cannot import agent-planted cwd modules.
- When shrinking `instruction.md` by moving detailed format rules into an agent-visible note, audit every exact output column and report container type. Deep review can still fail if a ledger column's event-specific meaning, empty-frame encoding scope, or JSON object-vs-array shape is enforced but not explicitly stated in either the prompt or visible note.
- For file/report provenance fields, state the exact path frame for each field: manifest-relative, output-root-relative, input-root-relative, or absolute. A byte-correct solution can become a task/verifier issue if the verifier silently expects relative paths, so add a visible note and a direct hidden assertion for path class.
- For receipt/tree digests over generated payload directories, disclose both the JSON container shape and the root used for relative paths. "Sorted rows" is not enough if the verifier expects one compact canonical JSON array instead of JSONL, or paths relative to `files/` rather than prefixed with `files/`.
- If static checks require absolute paths in `instruction.md`, avoid putting bare relative output/report examples in backticks. To disclose a relative JSON suffix, show the absolute copied file path under `/app/...` and say the report stores the string after removing the absolute output prefix.
- When pass@ feedback fixes a real ambiguity but prior agents solved the main workflow, pair the fix with a disclosed subsystem that changes multiple outputs together. For policy-driven file filters, validated sidecars with decoys should affect selection, score, stale/renewal timing, copy destination, provenance, and counters, with both visible and generated hidden witnesses.
- For audio/session repair tasks, report fields that sound like chunk sets (`tombstones`, `repairs`, `silence`) need explicit JSON type and count/list semantics. If pass@ failures cluster on that ambiguity while WAV bytes and hard algorithmic rules are solved, fix the schema and add a real disclosed stateful audio crux, such as intra-chunk feedback folds with visible and hidden witnesses.
- For optional sidecars, QC B5 may ignore a complete top-level prompt if the visible in-box packet has no rows exercising those sidecars and fixture notes only list headers. Mirror exact operations/signs/rounding in the shipped notes and include a compact visible witness that makes every advertised sidecar counter nonzero.
- For color/audio arithmetic with clamps, a nonzero operation counter does not prove boundary behavior. Add witnesses where values cross both the lower and upper bounds so modulo, wraparound, or missing-clamp mutants change byte-exact artifacts.
- If enforced similarity reports both instruction and verifier above threshold, treat the current artifacts as too close even if an older duplicate-check sticky says UNIQUE. Make a substantive semantic addition that changes outputs, reports, visible data, hidden generation, and verifier structure; pure prose edits or helper renames are unlikely to move a 0.98+ verifier score far enough.
- If several latest-head similarity runs are no-verdict infra (`HTTP 000`, `400`, or `503`) and a later recovered run posts real 0.98+ duplicate scores, stop empty-commit retries immediately. Redesign the task surface across instruction, schema, fixtures, solution, metadata, and verifier, then rerun oracle/nop locally before pushing.
- If a first semantic addition still leaves verifier similarity above threshold, add a branch earlier in the oracle pipeline rather than stacking another output transform. Candidate gating sidecars, selection-window rejects, or new validation buckets can change verifier structure and give QC/pass@ a clearer mutant than another late render effect.
- When a small QC-only fix is blocked by enforced similarity, prefer a new exact audit/report artifact over cosmetic rewrites. Require it in the prompt, generate it in the reference and solution, parse it strictly in `tests/test_outputs.py`, and make at least one value depend on the same semantic crux that caused the QC retry.
- If an audit artifact lowers neither instruction nor verifier enough, combine two moves: add another exact derived deliverable with a manifest hash binding, and split bulky verifier helpers into a non-collected support module so the compared pytest file is structurally small and task-specific.
- For byte-exact JSON/JSONL artifacts, do not rely on phrases like "sorted keys" when the verifier compares raw bytes. Define canonical object bytes once: key sort order, compact separators, and trailing newline policy for JSON files and JSONL rows. For capped accumulation rules, state whether the cap truncates the final contributing item or skips it entirely.
- If Stage-1 `essential_difficulty` fails because a task is fully specified transcription plus byte-exact output, do not defend the volume. Add a fair evidence-mined subsystem that solvers must recover from visible data and that varies in hidden fixtures, then route that recovered value through selection, ranking, accounting, and receipt/provenance checks.
- If pass@5 reports 5/5 solved and explicitly says there is no valid anchor fail, add a disclosed mechanic that composes with the existing pipeline rather than another cosmetic wrapper. For policy/file-filter tasks, byte-window proof rows and population-dependent bundle promotions are useful because they force solvers to carry payload hashes, temporal applicability, tag mutation, bucket caps, copied paths, audit tokens, and summary counters as one state machine.
- If pass@2 still solves after adding validation/selection sidecars, add a disclosed subsystem that changes the physical artifact bytes as well as metadata. For file/media filters, ordered mask/xor/clip operations against the evolving payload are a fair escalation when they are marker-validated, affect ranking/tags/caps, change copied bytes, and are bound into report digests and hidden fixture diversity.
- If pass@2 has a reward-0 run but classifies it as `in-progress-timeout`/`low_timeout` at 3600s, do not raise `[agent].timeout_sec` above the hard ceiling or treat it as infra. Add protected, spec-disclosed interaction witnesses that can fail after an agent confidently finishes: old valid rows that only increment counters, chained state mutations that change later validation ranges, retags that activate bundles, and bundle retags that alter caps/copy paths.

## 2026-07-25 Platform Updates (Dynamo team, Slack)

- **`DaytonaAuthorizationError` outage is FIXED.** For a window on/around 2026-07-24 to 2026-07-25, `pass2` trials aborted in ~30-40s with `DaytonaAuthorizationError: Failed to create snapshot: Access denied` during sandbox provisioning — before any agent ran (0 solved · 0 valid-fail · N infra/setup-timeout; all rubric criteria NA). The Dynamo team has resolved it; if a task was blocked by this, simply **rerun** (close→reopen the PR, or `/rerun` if admin) and it will no longer be blocked. Reminder from the stump guide: infra/setup/provider failures are NOT difficulty signals — never change validated task logic in response; rerun after recovery.
- **New pass@2 hardening-hint feature.** When a task does not clear the pass@2 check, the pipeline now auto-posts a comment with ONE personalized suggestion for making the task harder. It is only a hint: it never blocks the task/PR, you get at most 2 suggestions per task per day, and it does not change how tasks are reviewed, accepted, or paid. Use it as an input during creation/revision, alongside `PROJECT_DYNAMO_STUMP_GUIDE.md`.
- Stage-1 `review / review` failures with no rubric verdict and logs like `API Error: Connection closed mid-response`, GitHub API connection errors, or artifact upload timeouts are infrastructure/provider failures, not task-design evidence. Prefer `gh run rerun --failed` when allowed; if private fork permissions return 404, retrigger with a tree-identical amended commit instead of changing task logic.
- If enforced `review / cosine_similarity` reports instruction/verifier similarity near 1.0 after a retry redraw, do not trust an older legacy UNIQUE sticky. Make a substantive semantics-preserving change to both compared artifacts, ideally by documenting and testing a previously advisory edge case, then rerun local validation before pushing.
- For enforced similarity, check the job script/log to see exactly which files are compared. If it raw-files only `instruction.md` and `tests/test_outputs.py`, lowering verifier similarity may require a structural refactor of `test_outputs.py` itself, not merely adding an imported helper or renaming internals. A compact test wrapper plus imported support module can preserve verifier behavior while changing the compared artifact.
- If a pushed version clears similarity but fails static token limits, do not follow with a prompt-only trim. The next enforced similarity run may compare the unchanged verifier against the stored PR version and return ~1.0. Trim with margin and pair the rerun with a meaningful verifier-coverage addition plus a structural `test_outputs.py` reshape.
- After multiple prompt-only retries, the enforced similarity service may effectively make prior PR shapes part of the comparison surface. If instruction remains high despite large rewording, stop synonym editing and add a fair, disclosed artifact or mechanism that changes solution, reference, verifier, and instruction together.
- For reusable CLI verifiers, compute the protected expected JSON before executing the submitted tool, run the tool on a throwaway copy when possible, and recheck pinned visible inputs after execution. Otherwise a malicious artifact can rewrite the same input tree that the oracle reads and turn a non-general solver into reward 1.
- AVA `sound_verifier` blocks reusable CLI tasks when visible tests only hash pre-staged `/app/...` outputs and never invoke the submitted tool on the shipped vault. - AVA `verifier_coverage` treats `importlib.spec_from_file_location` as a bypass surface even for mutant/reference probes. Prefer subprocess on a mutated script file, or `compile`/`exec` under `__name__ != "__main__"`, instead of dynamic module load.
- Any public rule with a tie-break, sentinel value, clamp boundary, or no-trigger default needs a protected witness where changing that one rule changes output. A visible example or prose-only disclosure may not satisfy QC's hardcodability probes.
- When a QC-only patch receives real enforced self-similarity scores near 1.0, stop no-verdict retry behavior. A new exact companion artifact, digest report, or audit output that is required in `artifacts`, generated by the reference, and compared on visible and hidden packs is a stronger way to both clear similarity and preserve reviewer trust.
- For reverse-engineering puzzle tasks, a profile/audit artifact can be a clean cosine and review fix: require an ordered constants report plus residual replay counters, generate it from the same inferred profile as the solver, and verify it with strict JSON equality. This changes the comparison surface while reinforcing determinacy instead of adding cosmetic prose.
- For reverse-engineering renderer/profile tasks, calibration fixtures that isolate one constant on a zero-background pixel are usually too easy for pass@. Keep the function family explicit, but make visible probes mix constants with documented heat, decoration, flare, or overlay equations so solvers must invert and cross-check the profile instead of reading table values directly.
- For calibration-inference game tasks, avoid relying on charge/signature transitions alone to pin exact drift-like constants. If a value also affects scoring through a gated term, include visible fixed-script probes where the gate is on and the multiplier is nonzero, so QC cannot construct a calibration-identical alternate profile that changes hidden puzzle answers.
- For gated arithmetic terms with multiple coefficients, include separate visible and protected witnesses for each coefficient, and make verifier inference branch-aware. A "pulse" calibration row should be ignored or rejected unless the gate actually fires; otherwise non-firing rows can overwrite constants and QC can produce false oracle failures.
- For optimizer tie-breaks, tied data alone may not catch a deleted tie-break when the oracle enumerates candidates in the same lexicographic order as the rule. Feed the oracle from a deterministic order that differs from the documented tie-break and assert at least one equal-score witness's selected coordinates.
- For calibration-inference games, a formula using `min(previous_rank,current_rank)` needs visible/protected pair probes in both rank orderings; otherwise QC can replace it with `previous_rank` or another same-valued rival. Likewise, drift constants that affect both modulo charge and modulo pulse gates should have score-bearing pulse witnesses for every terrain/gate class, or an explicit canonical residue range, so `drift + cycle` mutants cannot preserve calibration.
- For profile/audit outputs, every strictly graded counter needs an explicit row universe and inclusion predicate in agent-visible text. Naming fields such as `single_rows` and `pair_rows` is not enough; say exactly which calibration rows count and what structural condition qualifies them.
- For byte-exact media/file artifacts, state every serialized field variant in agent-visible instructions or fixture notes, especially non-empty encodings that are easy to assume differently. For sidecar counters, specify whether counters are row/identity-based or per-application; duplicate packet/record rows can make a per-application reference silently overcount a single selected repair or marker.
