Recover the canonical timeline from the damaged reel in `/app/data/reel.bin` and the publication ledger in `/app/data/manifest.json`. Write exactly two outputs: `/app/recovered/timeline.json` and `/app/recovered/contact_sheet.ppm`.

The reel starts with the ASCII magic `DYNREEL1\n`, followed by records. Each record is: 8 ASCII bytes `chunk_id`, one codec byte, one width byte, one height byte, 8 ASCII bytes `base_id`, a little-endian uint32 payload length, payload bytes, and a little-endian uint32 CRC32. The CRC32 is computed over every record byte before the CRC field, starting at `chunk_id`. Reject records whose CRC does not match. All valid frames are RGB24 with the manifest width and height.

Codecs:
- `0`: payload is raw RGB24 pixels in row-major order.
- `1`: payload is RGB run-length encoding: repeated groups of one count byte followed by three RGB bytes. Expand each RGB triplet `count` times.
- `2`: payload is run-length encoded XOR data in the same group format as codec `1`. Expand it to RGB24 length, decode the valid record named by `base_id`, then XOR each expanded byte with the corresponding base-frame byte. Resolve `base_id` from the set of valid reel records, not from the final timeline; a codec-2 base can be superseded out of the timeline or can itself be another codec-2 record.

Build the timeline using only manifest chunks with `published_ms <= cutoff_published_ms`. Manifest rows may be duplicated; the first retained row for a `chunk_id` is authoritative, and later duplicated `chunk_id` rows are replay noise even if their `frame`, `pts_ms`, or `published_ms` differ. A retained row with `supersedes` removes that older `chunk_id` only if the retained row is within the cutoff; apply this rule through multi-step supersession chains. Late corrections after the cutoff do not remove the earlier chunk. After applying those rules, each frame number must have exactly one surviving chunk.

Create `/app/recovered/timeline.json` as UTF-8 JSON with exactly these top-level keys: `width`, `height`, `frame_count`, `fps`, `frames`, and `scene_cuts`. `width`, `height`, and `fps` come from the manifest. `frame_count` is the number of recovered frames. `frames` is sorted by increasing frame number; each item has exactly `frame`, `pts_ms`, `chunk_id`, `published_ms`, `sha256`, and `motion_score`. `sha256` is the lowercase SHA-256 hex digest of the decoded RGB24 bytes for that frame. `motion_score` is `0` for the first frame and otherwise the sum of absolute byte differences versus the previous recovered frame. `scene_cuts` is the list of frame numbers whose `motion_score` is at least `250000`, excluding the first frame.

Create `/app/recovered/contact_sheet.ppm` as a binary PPM `P6` image. Its width is `manifest.width * frame_count`, height is `manifest.height`, max value is `255`, and the pixel data places the recovered frames side by side from left to right in timeline order. Use the exact header form `P6\n<width> <height>\n255\n`.
