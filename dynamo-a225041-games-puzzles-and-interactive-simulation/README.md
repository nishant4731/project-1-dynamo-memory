# Signal Bastion Development Notes

This task was designed as a code-repair benchmark after output-only search variants proved too easy for agents to certify mechanically. Its synthetic fixture resembles the authoritative server-side round resolver, cooperative route planner, relay stabilizer, rollback controller, and effect VM used by a small deterministic multiplayer game: registration order is deliberately independent of unit IDs and input array order, blink destinations require global allocation before ordinary movement, living-start eligibility is snapshot-bound, routes require collision-free joint optimization, relay calibration has local incompatibilities but a directed global phase residue objective, replay corrections are certified by stateful future branches, and accepted frames are chained to canonical post-state hashes.

The visible suite is intentionally diagnostic rather than comprehensive. It exposes two engine failures, a simple relay calibration, one replay happy path, and only commutative VM arithmetic. Hidden tests cover only branches stated in `RULES.md`, with exact assertions and no undisclosed conventions. The verifier combines an 80-actor preference-ranked blink matching problem with post-blink movement, a 1,500-unit iterative movement chain, malformed duplicate-command filtering, start-dead defeat accounting in the shared registration-ordered defeat phase, globally optimal six-agent routing with absorbing goals and edge conflicts, relay choices that require combining disconnected components plus large acyclic and single-cycle components under a global modulo objective, same-relay option bans without graph self-edge distortion, wrapped serial order after recursive state/head branch certification, and bytecode control-flow dataflow with dormant unsafe paths, invalid dormant slots, and balanced loops.

For local review, build `task/environment`, run pytest in the resulting image for the no-op case, then mount `task/solution` and `task/tests`, execute `solve.sh`, and run both test suites. No external data or service is involved.

Schema note: the current Dynamo static checker requires a non-empty `[task].description` in `task/task.toml`. The substantive difficulty, solution, and verifier descriptions still live in `[metadata]`.
